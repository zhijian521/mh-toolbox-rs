## 1. 审查发现

按「会不会真的出事」排序，不按「改起来容易」排。

### 1.1 阻断级（现在不做，后面要付利息）

#### A. 一行静态检查都没有 —— ✅ 已修（第一批 1–3）

`ls` 实测：无 `.eslintrc*`、无 `eslint.config.js`、无 `.prettierrc*`、无 `.editorconfig`、
无 `rustfmt.toml`、无 `clippy.toml`。唯一的质量门是 `package.json:7` 的
`vue-tsc --noEmit && vite build`——它只查类型，不查「有没有写 `v-html`」「有没有用
`:any`」「Vue 属性顺序对不对」「有没有未使用的 ref」。

旧仓 `mh-tool` 有 `eslint.config.js`（含 renderer / main / tests 三组环境分离）。新仓连
`eslint-plugin-vue` 都没装。

**为什么必须现在做**：现在 21 个文件，接上 lint 大概是改十几处；等 100 个文件、几十个
页面时接，要么一次性改几百处，要么关掉规则假装通过。**规范的价值在于「从第一天就没有例外」**。

#### B. 零测试，而项目定位是「拿旧仓当 oracle 做差分」 —— ⏳ 待第三批

README 写着「6333 行领域逻辑是唯一可信规格」、`tests/fixtures/legacy-domain/` 要 vendor 进来
做逐字段对比。但：

- 没有 `vitest`（前端）
- `src-tauri` 下没有任何 `#[test]` / `tests/` 目录
- 没有 harness 骨架

现在 Rust 只有 135 行，`data_dir()` 这种纯函数已经可以测了。**harness 要在写第一行领域代码
之前就建好**——这是记忆里已经写下的结论，但还没落地。

#### C. 工具链版本没锁 —— ⚠️ 部分完成（`engines` 与 `rust-toolchain.toml` 已加，无 `.nvmrc`）

- `package.json` 无 `engines`、无 `packageManager`（实测 `node -e` 输出「无」）
- 无 `rust-toolchain.toml`；`src-tauri/Cargo.toml:6` 的 `rust-version = "1.77"` 只是**最低**
  声明，不锁实际版本
- 无 `.nvmrc` / `.node-version`

本机是 node 22.22.2 / npm 10.9.7。换机、重装、或者以后接 CI，只要 node 主版本跳一档，
`vite 6` / `vue-tsc` 的行为就可能变，而这种变化会伪装成「代码坏了」。

#### D. 提交信息无强制 —— ✅ 已有校验器（`npm run lint:commits`，未并进 `check`）

`git log` 实测：66 个提交里 21 个带 `type:` 前缀（前 45 个是旧项目历史，不算）。
最近 20 个**全部合规**，说明习惯已经养成。但这是自律，不是机制——旧仓有
`scripts/check-commits.mjs` + `npm run lint:commits`，本仓没有。

### 1.2 结构级（影响后续每一步）

#### E. 没有路由，8 个页面靠 `v-if` 硬编码 —— ✅ 已修（第二批 8）

```ts
// src/App.vue:25
const current = ref('settings');
// src/App.vue:38
<SettingsView v-if="current === 'settings'" />
```

加一个页面要同时改两处：`pages` 数组（`App.vue:14-23`）和模板里的 `v-if` 分支。
七个占位页共用一个 `PageHeader` + 占位块，这个 if-else 会长成 8 个分支的 switch。

Tauri 跑的是本地文件，`createWebHashHistory()` 零成本，不需要服务端配置。收益是
每页一个路由、可深链接（以后「从托盘直接打开收益页」）、浏览器前进后退可用、
`SettingsView` 的 667 行能被路由懒加载摊开。

#### F. `SettingsView.vue` 667 行 / 8 个 section —— ✅ 已拆（第二批 9）

`src/views/SettingsView.vue` 里：外观（86）、原子组件（107）、色板（148）、字号阶梯（161）、
控件（174）、图标（254）、结构（282）、关于（316），每个 section 都带一段 300–100 行的 scoped 样式。
（本节是拆分**前**的测绘。其中两张卡已删：「控件」于第 5 小批删掉——组件齐了之后它只是
`SlotButton` / `SegmentedPills` / `CostSwitch` / `BaseCheck` 的第二份演示；「结构」于第 6 小批删掉——
文武线与账线的实例就是每张卡自己的 `.frame`，不必再拿一张卡讲同一件事。第 7 小批起开发用的四张卡
搬到 `views/dev/`，现为 2 个 section——验收面在 `#/dev`，见 §2.4-19。）

这不是样式问题，是「一个文件承担了 8 件事」。而且它同时是**设计系统的验收面**——
`SettingsView.vue:20-22` 的注释写着「以后新增控件先加进这一块」。这意味着它只会继续变长。

#### G. 没有状态层

`current` 在 `App.vue`，`mode`/`scale` 在 composable（侧栏的 `collapsed` 已随竖向滑块一起删除，
50px 的栏不需要第二套宽度）。
到目前够用，但业务数据一进来（角色列表、流水、装备）就需要一个明确的答案：
Pinia 还是 provide/inject？现在没定，第一个做业务页的人会自己发明一套。

#### H. 设计令牌是双份，而且已经漂了 —— ✅ 已修（第二批 12）

`src/styles/tokens.css` 与 `design/tokens.css` 是两份手工维护的副本。
`diff` 实测已经出现 4 处差异（`@font-face` 路径、两处注释措辞、`base.css` 里
`.page-content` 只在 `src/` 有）。记忆里写着「改令牌两边都要改」——这句话本身就是问题：
**凡是需要「记得两边都改」的东西，迟早会不一致。**

#### I. IPC 契约是两份手抄

```ts
// src/services/desktop.ts:11-18
export interface AppInfo {
    productName: string;
    version: string; /* ... */
}
```

```rust
// src-tauri/src/lib.rs:10-16
pub struct AppInfo { product_name: String, version: String, /* ... */ }
```

`#[serde(rename_all = "camelCase")]` 让两边字段名对得上，靠的是人记得加这个属性。
命令只有 2 个时无所谓，20 个时必然出错。`tauri-specta` 未上（记忆里已列为计划）。

#### J. `crates/` 目录还不存在

规划里领域层要拆成独立 crate（`mh-domain` / `mh-store` …），但根目录没有 `crates/`。
现在不建也没事，但**第一次写领域代码时如果顺手塞进 `src-tauri/src/`，就再也拆不出来了**。
应该在建目录的同一刻把边界写进文档。

#### K. `design/icon/` 里躺着 3.9 MB 废弃产物 —— ✅ 已清（第二批 13）

> **2026-11-01 追补**：`old/` 已删（`make-preview.py` 里的「与上一版对照」段落一并去掉）。

### 第 20 小批：天眼后「附近」消失，两层红降透明度（2026-11-01）— **✅ 已完成**

两条用户反馈：

1. 「使用天眼之后，描述中的**附近会去掉**，就变成真实坐标了，不用显示范围，只显示
   这个坐标即可。」
2. 「两个背景有点太遮挡地图了，是提高透明度还是换个颜色？」

#### 一、天眼状态原来只认「处」，认不出「没有附近」

`RevealState` 原来只有 `nearby` / `exact` / `unknown` 三档，`exact` 只在读到「处」
时成立。而用户实测：**开天眼是把「附近」两个字整段删掉**，不给替代字，句子变成
`去江南野外134,54抓巳时四刻偷尸鬼。`——句尾是**空的**。这种帧原来落到 `unknown`，
照旧画 ±50 范围，天眼白开了。

补 `silent` 一档，**并且必须与 `unknown` 分开**：`silent` 是严格句式匹配成功、
确认句尾为空；`unknown` 是兜底句式，那一层压根没捕获句尾。混成一个会同时错两头——
当成 `exact` 则每条兜底任务都画成一个点，当成 `unknown` 则天眼任务永远停在范围上。
实现上靠 `buildTask` 第 6 参的**空串与 `undefined` 之分**（严格传 `hit[5] ?? ''`，
兜底传 `undefined`），`revealOf()` 里三种取值分开判。

#### 二、`silent` 的分数定 1，是为了让误判能自己退回去

这是本批最不显然的一处。完整度的句尾档原来是「有 / 没有」两档，现在三档：

| 状态               | 分  | 理由                                       |
| ------------------ | --- | ------------------------------------------ |
| `nearby` / `exact` | 2   | 有字为凭                                   |
| `silent`           | 1   | 「附近」消失大概率是真开眼，但也可能是漏读 |
| `unknown`          | 0   | 兜底句式，结构都没了                       |

若给 `silent` 也记 2 分，它会和真 `nearby` 同分：某一帧漏读「附近」被判成精确点之后，
要等三帧（3.3 秒）才能被纠正，用户已经照着一个点跑错方向。定 1 分之后，下一帧读回
「附近」就是**更高分**，按「更完整立刻换」立刻退回范围。

代价是「`nearby` → `silent`」成了降分，按分数永远走不动，会死锁在范围上。所以那一步
由 `revealStep()` 单独放行，且**要求连续 2 帧**：读到「处」是一个明确的字（一帧即换），
「附近」消失是**缺失**，而缺失比存在弱——NPC 走过去糊掉一行字通常一两秒就过去，
凑不满两帧，而真开眼之后「附近」永久不再出现。

#### 三、两层红压到 0.24 / 0.42，边框从 1px 加到 2px

原值 0.62 / 0.70 下地形基本只剩一团糊。这次改的不是颜色而是**分工**：

- 填充只表示「这一片有鬼」，alpha 降到 0.24（官方 ±50）/ 0.42（高概率区域），暗色 0.30 / 0.48；
- **范围的边界交给边框**，从 1px 加到 2px——填充只剩两成后，那圈线是范围唯一的凭据，
  1px 在树丛与山棱的线条里会被读成地图自带的一格。

没换颜色、没做斜纹：斜纹与虚线在写实地形上都会与树丛、小路的纹理打架，读起来像
地图自带要素。两层仍靠**明度差**区分，不靠线型。

#### 为什么不能「把分隔符写成可选」

这是本批最关键的判断。`(\d{1,4})` 是贪婪的，分隔符一可选，`119107` 会切成

在正则之外另起一层救**。

#### 第三层：靠地图值域枚举切分点

`splitCoordDigits()` 枚举所有切法，只认 `x ≤ maxX 且 y ≤ maxY` 的那一种。
这条判据硬得意外——20 张图 maxX 最大 640、maxY 最大 210，都是三位数：

| 位数          | 可能的切法                  | 收敛结果           |
| ------------- | --------------------------- | ------------------ |
| 6 位 `119107` | 1+5 / 2+4 / 3+3 / 4+2 / 5+1 | 只有 3+3           |
| 5 位 `13454`  | 1+4 / 2+3 / 3+2 / 4+1       | 只剩 3+2           |
| 4 位 `1234`   | 1+3 / 2+2 / 3+1             | 取长度差最小的 2+2 |

- **前导零直接排除**。第一版把 `12105` 判成平手（`12,105` 与 `121,5`），测试红了
  才发现 `121,5` 粘连后是 `1215`（4 位）——多出来的那个 `0` 只能属于前一段。
  这条比「两段等长」硬，加上之后 `12105` 立刻唯一定成 `12,105`。
- **值域筛不干净就判失败**。`12115` 在 640×120 的大唐境外既能切 `12,115` 也能切
  `121,15`，两段都正数开头、都合法、gap 都是 1。没有第三条信息，**不猜**——
  错几十格的坐标比没有坐标更坏，用户会照着走过去而界面一切正常。
  地名没对上底图时同样放弃：没有值域就没有判据，只剩「两段等长」这一条猜测。

这一层的句尾只在**明确读到「附近 / 处」**时才采纳，读不到一律 `undefined`
（→ `unknown`，照常画范围）。理由：缺逗号本身就说明这一帧不完整，再拿它去判

这个坐标是**算出来的**，不是读出来的，用户有权怀疑它。切不开的帧留

选定**朱书**：朱红数字直接写在地形上，没有底板、没有边框。

#### 一、为什么前两轮候选全被否

第一轮给的是靶心、圆点+引线、缺口准星、朱印双线框——四个都在做同一件事：
**把一块牌子贴到地图上**，只是边框和颜色不同。它们都是「现代地图 POI 标注」
的变体，与这套纸墨界面不是一个语言。

第二轮换骨架（朱印反白 / 朱书 / 朱笔圈 / 燕尾签），并统一把数字换成霞鹜文楷
（就是正文那支字，系统里装着 `LXGWWenKai-Medium.ttf`，PIL 能直接读，所以候选图
与真机是同一种字形）。这一轮才拉开方向差距。

方法上一条：**候选必须 1:1 出图**。同一套标记放到 5× 下四个都精致，1:1 下才能
看出谁读得清；另外补了一张「同尺寸横排」，专门用来比小尺寸下的可读性。

#### 二、选定方案的实现

- 中心：朱红实心点 r=4，外面一圈纸白细环 r=5.1、1.3px。环不是装饰——没有它，
  点会与深色山地、水面融成一片。
- 坐标：`13.5px` 霞鹜文楷，朱红 `--map-seal-ink`，**无底板无边框**，写在点右侧
  11px；右侧放不下（贴边、「图外」让字变长）时翻到左侧。垂直方向与点同高，
  只夹到不出图——挪走就读不出「这串数字属于这个点」。
- 可读性靠纸白描边。**必须先 `strokeText` 再 `fillText`**：`strokeText` 的
  `lineWidth` 骑在字形轮廓上、内外各一半，随后填字把朝内那半盖掉，净剩向外 1px；
  反过来先填后描会把笔画本身吃细。
- 描边宽度试过 1.2px → 糊。「134,54」的「4」在 13px 楷体上笔画只有一像素宽，
  1.2px 的白边几乎把字口吃掉；收到 1.0px 并把字号提到 13.5px 之后才读得清。

#### 三、新增一组「不翻面」的令牌

`--map-seal` / `--map-seal-ink` / `--map-halo`，**全站唯一不带 `light-dark()` 的
颜色**。理由：底图是游戏截图，主题切暗色时它一格都不变；标记要对抗的是地形，
不是主题。实测跟着翻面会变糟——`--cinnabar-ink` 在暗色下是亮粉朱 `#b85b49`，
压在**同一片**绿地上比亮色主题还糊。描边同理，用 `--paper` 的话暗色下成了近黑，
等于给朱字镶一圈黑边。

这一组在 `tokens.css` 里用整段注释写明「故意的」，免得以后有人当成漏了 `light-dark()`
给「修」回去。

#### 四、顺带

- 范围模式（未开眼）的坐标标签**一点没动**，仍是纸底 + 墨字。两种模式的视觉差异
  这次是**故意**的：范围是一块区域，需要边界；精确点是一个位置，不需要容器。
- 探针新增 `?m=eyeout`：开眼 + 坐标越界。文字多出「图外」两个字会变长，用来验
  翻左分支还准不准（碗子山 600 > 95，必然贴右边）。

#### 一、必须修：一条 CI 任务在干净检出上必定是红的

`rust-test` 只跑 `cargo test --lib`，而 `tauri::generate_context!` 在
`custom-protocol`（默认 feature）开启时按 `frontendDist` 去读 `dist/`，
目录不存在**直接 panic**，不会提示「缺文件」。`dist/` 不入库，所以那个 job 原本
在干净检出上必然失败；本机绿只是因为工作区里恰好留着上次构建的 `dist/`。

修法是给它补上前端产物（`npm ci && npm run build`），而不是改成
`--no-default-features`——后者测的是另一套 feature，与真实产物不一致。

顺带把那个文件开头「本机跑什么这里就跑什么，所以只有一步」的说法改掉：实际是三个
job，其中 `cargo fmt --check` 与 `cargo test` 都**不在** `npm run check` 里。

#### 二、发布版唯一的崩溃点没人看得见

`lib.rs` 结尾是 `.expect("Tauri 应用启动失败")`，而 `main.rs` 在发布版是
`windows_subsystem = "windows"`——没有控制台，那行字写进 stderr 之后就消失了。
用户看到的只是窗口闪一下。WebView2 运行时缺失、建窗失败这两类**新机器上最常见的失败**
正好都走这条路。改成 `report_fatal()`：先写 `%APPDATA%\mh-tool-v2\startup-error.log`，
再弹一个原生 `MessageBoxW`，把日志路径写在对话框里。
