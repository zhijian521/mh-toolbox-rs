# 游戏资源规范（GAME-ASSETS）

> **一句话**：凡是「梦幻西游本身长什么样、有什么东西」，进 `public/game/`；凡是「我们怎么读它、
> 怎么判断」，留在代码里。目的只有一个——游戏改版时**换文件，不改代码**。

## 1. 判据：什么东西算「游戏资源」

三条全部满足才进 `public/game/`：

1. **内容变了，代码一行不用改**。换底图、加门派，改的是文件与清单，不是 `.ts`。做不到说明它是逻辑。
2. **内容来自游戏，不是我们编的**。门派名、地图名、坐标域上限、任务句式是客观事实；
   「高概率区域画 24% 红」是我们的设计决定，不是游戏事实。
3. **丢了它应用「少一块」而不是「崩掉」**。资源缺失要退化成空状态；缺了就跑不起来的是依赖。

反向判据更好用：**「游戏改版后我需要改代码吗？」**——要改的就是代码。

**`icons/` 下只允许有子目录**，目录名就是文件名前缀；加新类目（任务图、NPC、宝石）就新建同名
目录。这两条由 `game-icons.test.ts` 的「图标目录结构」断言盯着，不是口头约定。目录与清单一一对应
（`skill/` `story/` `active/` 三份共用一个 `icons.json`，因为它们来自同一块 4×3 面板、同一个脚本）。
三个子目录各有一份 README 写「放什么、怎么命名」，这份文档写**规则本身**——那三份会随
`npm run build` 进 `dist/`（约 4KB），有意为之：它们给「半年后往这里丢一张 png 的人」看，放在目录
里才会被看到，放 `docs/` 只会被忘掉。

## 3. 三条硬规则

### 3.1 放 `public/`，不放 `src/`

Vite 会把 `src/` 里的资源**改名加哈希**，而清单写的是文件名，替换后必须还能对上。`public/` 是唯一
「原样拷贝、不改名」的目录。代价：不经打包器优化、没有缓存指纹、拿不到 `import` 的类型检查。
对一批**会随游戏版本整体更换**的文件，这个代价划算。

### 3.2 目录只在代码里写一次

清单里**只写文件名**，目录由加载函数拼：

```ts
// src/services/ghost-maps.ts
const MAP_DIR = `${import.meta.env.BASE_URL}game/maps/`;
```

```json
{ "id": "aolaiguo", "name": "傲来国", "img": "aolaiguo.webp" }
```

不写 `"img": "/game/maps/aolaiguo.webp"`：目录名会重复进 20 条记录，换一次目录要改 21 处，**漏掉的
那条只有运行到那张地图时才 404**——页面一切正常，只是不显示底图。`import.meta.env.BASE_URL` 也不能
省：写死 `/game/maps/` 在当前 `base: '/'` 下等价，换子路径部署时整体失效且无报错。**已知例外**是四
个测试文件里的 `import mapsFile from '../../public/game/maps/maps.json'`——模块解析要求字面量，改目录
时按 IDE 全局替换一次改完。除此之外**同一文件里不许再写第二个路径常量**（`ghost-maps.test.ts` 因此
改用 `readFileSync`，让目录只出现一次）。

### 3.3 文件与清单同目录

`maps.json` 和那 20 张 webp 必须住在一起：这是**唯一能保证「改一份忘一份」只有一次编辑动作**的办法。
加一条记录却忘了放图，`npm run check` 当场失败——`ghost-maps.test.ts` 四条断言盯着：**缺图**、
**孤儿图**、**`img` 带了目录**、**id 重复**，四条都读真实目录（假清单只能证明「假的东西对」）。
不要为了「JSON 归 JSON、图片归图片」分两个目录：那是按文件类型分，而资源是按**改动时一起改**分。

## 4. 命名

| 对象     | 规则                                                      | 例                                  |
| -------- | --------------------------------------------------------- | ----------------------------------- |
| 图片文件 | `<id>.webp`，id 用拼音小写，与清单一致                    | `xiliangnvgou.webp`                 |
| 图标文件 | `<类目>/<类目>-<id>.webp`；一个实体多个图标时带子类与序号 | `school/school-skill-datang-1.webp` |
| 数据表   | `<实体复数>.json`                                         | `schools.json`                      |
| 记录 id  | 稳定唯一；**显示名可以改，id 不要改**                     | `datang`                            |

文件名会进 URL，所以只用 `[a-z0-9-]`；中文名放清单的 `name`——游戏改译名时只改 JSON，不动文件。

### 4.1 图标：一个类目一个目录

`icons/` 根下**只有子目录**，一张图都不许放。目录名 = 一级类目 = 文件名前缀（`skill/` 装
`skill-*`、`school/` 装 `school-skill-*`）。为什么不是「全平铺、靠前缀区分」（2026-11-04 之前 249 个
文件挤在一层）：**前缀是给人猜的，目录是给工具用的**（`ls icons/school | wc -l` 就是答案，切图脚本
能整目录重写）；**一个目录 = 一次改动**（换一批装备图只动 `gear/`）；**加类目不需要决策**（新建
`task/` 就完了）。判据与 §3.3 同源：按「改动时一起改」分组，不按文件类型分。

三条断言撑着（`game-icons.test.ts`，读真实目录、`import.meta.glob`）：**根目录下没有散图**（拦「往
icons/ 丢一个 png」这种最省事的做法）、**文件名以目录名开头**（拦 `skill/` 里混进 `gear-*`）、
**文档里列的类目目录都已有图**（这条是 2026-11-05 补的：当时本文档写了 `lingshi/`，仓库里却没这个目录，卡上四格一直是破图）。

### 4.2 图标：优先客户端原生图，截图只作名字与顺序的真值

能从客户端资源包拿到原生像素，就**不用截图切的放大版**：游戏面板里一格图标本体是 40×40
的源被放大渲染进 96 格子的结果，切下来再缩到 96 是二道手，过 webp q92 又损一次。
手画的图改版后必然对不上，第三方素材包与本客户端版本未必一致，混进去没人分得清哪个是哪个。

截至第 144 批，`skill/` `story/` `active/` `school/` `gear/` `weapon/` `lingshi/` `yupo/`
八类全部来自客户端；`slice.py` / `slice-school.py` 等切图脚本仍要跑，但它们现在只产出
**名字与顺序**，图片随后被 `import-*-icons.py` 整批覆写（**先切后导入**，反过来会把图
打回截图版）。只有 `item/` 还是旧系统带过来的图。

**最早从客户端导入的是灵饰与玉魄**（第 116 批）：那 22 张改从客户端资源里导入大图，见本节最后一条。
理由不是「客户端比截图更真」，而是灵饰截图那一格只有 94×94 且**自带游戏卡片底**，
在 40px 的槽里读作一块米黄方片；客户端本来就有透明大图，没有理由不用。玉魄更简单——
它从来没进过百科典藏的列表，卡上那两格一直是「首字印」，没有截图可切。

切图脚本四个 + 导入脚本五个，按面板形态分：

- `slice.py`——4 列 × 3 行卡片网格（生活 / 剧情 / 特技），靠检测找格子；
- `slice-school.py`——竖排 7 行门派面板（**只取左边那一列师门技能**，中间那列师门法术不收），横向
  固定坐标、**纵向每格量底边**，名字与 `schools.json` 做集合比对。**2026-11-07 起它只负责名字与顺序**
  （第 139 批）：切出来的图会被 `import-school-icons.py` 整批覆写，画面质量不再由它决定；
- `slice-gear.py`——百科典藏「装备」页，3 列 × 4 行、**列表可滚动**：列固定、行靠投影检测，滚动露出
  的半行（高 < 70）丢掉，重叠行按 `rows` 声明只取一次；
- `slice-weapon.py`——百科典藏「武器」页，同为 3 列可滚动，但**按位置定档**：官网 20 种 × 17 行
  （0–160 级）的顺序与游戏一致，先整体对齐到这 340 行得到该页偏移，再取 `level >= 60`。**不要按用户
  画的红线筛**（红线只标在每组开头，且红色图标本身会被红色判据误命中）。行定位用**格子间隙求相位**，
  不用内容投影：图标贴不贴格子顶因图而异，投影法会让每页偏 2~8px（返工过一次，见 `icons/README.md`）。
  取景与 `slice-gear.py` **完全同规格**（内缩 2 → 90×90 → 96×96）：卡片四角的卷云暗纹要靠四个格子
  拼成完整图案，内缩多一点就会缺一瓣；底边兜到面板边界的格子由 `has_band()` 拒收。
  **后五种是例外**（巨剑 / 灯笼 / 伞 / 双巨斧 / 棍）：它们在客户端的排列顺序与官网不同，双巨斧还
  拆成「乾」「坤」两件（各 17 档，含 160 的「非天」），截图又是乱序截的——这五种按「哪一页的
  第几格 = 哪组的第几档」写死在 `LATE_PAGES`，起始档靠三样互校：用户画的红圈、选中框 + 右侧
  详情、同组两页之间像素差 0 的 3 格重叠。**切到的档必须覆盖名字表每一档**：早先这里按「截图里
  没有 160 那一格」推断「九黎城没做 160 造型」，把两组的名字表各砍掉一条，清单少了两件、
  客户端里现成的 `非天（乾）/（坤）` 也没被用上（2026-11-05 用户从藏宝阁截图指出，第 121 批修）。
- `import-client-icons.py`——灵饰与玉魄**不从截图切**（2026-11-05 改，第 116 批）：读提取工程的
  `output/names.csv`，按物品名取客户端 `item120` 大图（透明底），裁透明边、最长边缩到 108、
  居中放进 120×120 画布。旧 `slice-lingshi.py` 已删——那一批一格只有 94×94 且自带游戏卡片底，
  40px 下读作一块米黄方片。`玄龙苍珀`（佩饰 140）本地缺 `item120`，只能放大 `item50`，
  清单里 `source` 字段写明，别拿官网小图凑。玉魄两件写进 `yupo/`，**不写清单**（两条固定记录，
  默认图标文件名由 `character-rules.json` 的部位规则持有）。

- `import-slot-icons.py`——装备与武器**也不从截图切**（2026-11-05，第 120 批起装备全量）：这两类
  合起来 312 件，**同名物品在客户端里不止一个**（`如意` 同时是环圈 / 法宝 / 道具，`龙筋` 同时是
  鞭与材料），按名字取会静默抓到别的道具，画面上只是「看起来像」。所以改按**物品编号段**定位：
  武器每组用「候选 id − 偏移」投票求起始编号（票数不过半直接退出），装备限定 `2000–2999` 段内
  再用**相邻锚点**收敛；末尾还有一道「解析出的编号必须沿清单递增」的断言。解码交给提取工程的
  `slot-icons.cjs`（按 MD5 定点解，不跑全量导出）。它**只覆写图片与 `source`**，id / 名称 / 等级 /
  顺序仍是 `slice-gear.py` / `slice-weapon.py` 的产物。`--only gear|weapon`、`--check` 分组与干跑。

- `import-school-icons.py`——门派技能**改从客户端资源包取原生 PNG**（2026-11-07，第 139 批）：
  读提取侧的 `index.csv` 与 `png/<门派>/<技能名>.png`，按**技能名**连到 `school-icons.json`

  id / 名称 / school / 顺序仍是 `slice-school.py` 的产物**，所以两条要连着跑。
  换的理由是清晰度：旧图「像素 96、信息 40×40」——那 60×59 是游戏把 40×40 放大渲染进格子的结果，
  再缩到 96 又插值一次。147 对按 48px 真实显示管线实测锐度 **+71%**，146/147 项变锐。

- `import-skill-icons.py`——生活技能同样**改从客户端资源包取原生 PNG**（2026-11-07，第 142 批）：

  `icons.json` 的 `groups.skill`，LANCZOS 归一到 96×96、webp q92。**只覆写图片与每条记录的
  `source`**，id / 名称 / 顺序仍是 `slice.py` 的产物，所以 `slice.py` → 本脚本要连着跑。

各写自己的清单（玉魄除外，见上）
——共用一份的话，后跑的脚本会把对方的分组整段覆盖，且不报错。

下面两条是 `slice-school.py` 截图路的判据，第 139 批换了来源之后**不再影响出图**（那批图现在直出
客户端原样），但脚本仍要能跑通——它产出的名字与顺序还是真源。

**别给图标「补成正方形」**：门派技能本体 60×57~59，补那几像素若填黑色，就成了上下各一条黑边，看着
正像图标被截断（踩过一次）；直接按 96×96 缩放，各向异性 1~3% 看不出来。

**底边必须逐格量，不能补整数像素**：同一批 21 张截图里，最后六家（女魃墓、天机城、花果山、东海渊、
九黎城、弥勒山）的图标列比前十五家高 1px，最底下一行是「描边 + 米黄底」混出来的半透明行（比上一行
亮 7~50 级），而前十五家那一行是本体自带的深色描边（低 10~23 级）——落在 96px 图上就是用户两次指认
的那道黄边。`dy: -1` 手工补偿没用（黄边只是从 1 行挪到另 1 行）；现在 `body_bottom()` 逐格找「描边 →
米黄底」最陡的变亮跳变，**跳变行比上一行亮就丢掉它**（两类相差 17 级）。结果：前十五家 59 行、后六家
57 行，各家 7 格完全一致，147 张末行亮度最高 49（此前 88）。`assert_no_pale_edge()`（末行亮度 > 130
报错）作为兜底留着。

| 处理过的坑                                             | 做法                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------- |
| 末行只有 1 项，那一行检测不到                          | 按相邻**最小**间距外推 3 行；外推位置没图标就跳过          |
| 某些页其中一列图标偏亮，检测不到                       | 同上：外推而非依赖全检出，否则首尾平均会把间距算成两倍     |
| 游戏给选中项画了一圈金框，会被裁进来                   | 掩膜里按颜色剔掉金框，再对框边缘复查、有金边就内缩 2px     |
| 导出的图标外面套了一圈米黄（用户原话「一圈都有黄边」） | 不垫背景、图标铺满画布；再按**色偏**把边缘残留的卡片底剥掉 |

前三条都试过「阈值调一调就好」，都不行——**间隙处的投影值正好等于阈值**，而且浅色图标与金色图标的
亮度分布相反，一刀切必然顾此失彼。

序号命名（`skill-01`）与名字表的对应由 `game-icons.test.ts` 盯着：**第 n 个图标的名字必须等于名字表
第 n 项**。错位不会让任何东西变红，只会表现为「强身术配了冥想的图」——图标都是纹样，没人能一眼看出。

### 4.3 召唤兽技能原图归档

`pet-*` 四个技能目录与 `data/pet-skills.json` 已接入召唤兽列表、详情、编辑与截图识别。清单由 `tools/game-icons/import-pet-skill-icons.py` 从已具名、已校正的独立素材包生成，中文名只在清单维护，文件按官网技能 ID 命名。

本批按用户要求保留原 PNG，尺寸有 30/40/50px，不放大、不改为有损 WebP。来源包括客户端原图和官网具名 GIF 转 PNG，清单逐项标记来源；这批已确认的官网补图不会冒充客户端资源。低级/高级反击与冥思已纠正，导入时校验四张已核对图片的摘要。详见 `public/game/data/README.md`。

`categories[].iconDir` 指向对应分类目录，`icons[].img` 只含文件名；`id` 为稳定字符串，`displayName` 区分同名技能的版本。缺图名称在 `missing` 保留，图片字段为 `null`。`services/pet-assets.ts` 按需校验加载，组件不复制名字表。

### 4.4 召唤兽头像与识别字段

`icons/pet-portrait/` 和 `data/pet-portraits.json` 由 `tools/game-icons/import-pet-portraits.mjs` 再生。
脚本只读客户端图鉴静态字典、THX 和 WPK，通过资源摘要确认原图；已具名的解包头像作为立绘补充，裁掉透明画布。
每项记录稳定编号、物种、文件名及资源路径 / 摘要或解包来源。玩家自定义名字与头像编号独立，改名不换头像。
流式客户端没有下载的头像，通过客户端 `cloud.json` 指定的官方资源端点补齐，解包后逐张核对 THX 的摘要。
当前召唤兽图鉴已全部覆盖（孩子系统另计），共 548 张头像和立绘；未来未取到的资源仍由 `missing` 明确记录。
导入使用 `node tools/game-icons/import-pet-portraits.mjs --download-missing`，默认只读本地包和
`.runtime/pet-portrait-resources` 缓存；下载仅用于离线导入，应用运行时只读随包资源。

`data/pet-panel.json` 维护七项属性、六项加点、资源上限字段、标签与别名，以及资质后续行顺序和五行名录；六项资质沿用
`character-rules.json`。数值解析与技能区域定位在 `views/characters/ocr/pet-*`，成功识别整只覆盖当前草稿，
未识别字段清空，不合并旧属性或旧技能；识别失败不改草稿。未读到名字时保留当前名字，不按自定义名字猜物种。
新增召唤兽只由“新增”按钮触发。点兽牌直接打开与装备一致的左右分栏修改窗，截图和手改共用一份表单；
属性、加点和资质沿用角色属性的票面行与数值槽。内丹和灵性仅兼容旧记录，不再提供界面。

## 5. 不放在这里

装备图标和截图识别通过 `services/game-data.ts` 的 `loadEquipmentNames()` 按需读取现有

`views/characters/gear-icons.ts` 按装备名匹配；未收录的低等级装备回退到对应类别的 60 级图，武器同名时按类别区分。
识别规则与浮片文字预处理位于 `views/characters/ocr/gear-panel.ts`、`gear-image.ts`，不属于资源表。

| ----------------------- | -------------------------- | ----------------------------------------------- |
| OCR 模型与字典（16MB）  | `src-tauri/models/`        | PP-OCRv4 通用模型，与游戏版本无关；走 Rust 打包 |

| 解析正则、ROI、纠错表   | `src/services/`            | 是「怎么读」                                    |

## 6. 游戏数据与实现边界

角色名录、部位规则、属性选项、强化系数、活动日程和游戏品类统一放在 `public/game/data/`。
“只改一个数”也属于数据，不再作为留在 TS 的理由。当前三张表：

| 表                     | 内容                                                                                       | 消费入口                      |
| ---------------------- | ------------------------------------------------------------------------------------------ | ----------------------------- |
| `character-rules.json` | 属性与修炼模板、部位/图标分组、特技特效/蓝字、属性选项与强化系数、召唤兽资质、OCR 标签名录 | `services/game-rules.ts`      |
| `activities.json`      | 活动名称、周期、时段及来源标记                                                             | `services/game-activities.ts` |
| `gameplay.json`        | 物价品类与旧名称线索、抓鬼容差和经验边界                                                   | `services/gameplay.ts`        |

生产代码不直接 import public JSON。`game-data.ts` 在启动边界并行读取、全部校验后统一安装，
完成首次加载尝试后再读取角色名册与物价、挂载应用；消费方同步读取服务导出的表。
模块顶层不能根据尚未安装的表派生数组或正则。任一资源失败时保留上一份有效缓存并允许重试；
首次加载失败仍挂载应用，保留用户存档的属性、修炼、装备和分类。角色页展示服务的统一状态与重试入口，
页面和名册数据层均暂停修改；重试成功只补全内存模板，不自动写盘，不能用空模板清掉已有记录。

稳定存档键与字段类型留在 TS，例如 `GearSlotName`；更改存档身份属于契约迁移，不能仅改资源。
OCR 分框、ROI、形近字纠错、句式正则与数值合理性检查属于解析算法；通用 OCR 模型仍在
`src-tauri/models/`。页签、配色和留白是应用策略；演示数据与回归样本是夹具，跟随页面或测试保存。

切图脚本与测试都直接读取这些 JSON，不再保留特技名单副本。真实表的完整性、安装原子性、
重试及缺资源保护由 `game-rules.test.ts`、`game-data-loading.test.ts` 与原图烟测覆盖。

## 7. 替换流程

- **换一张底图**：覆盖 `maps/` 下同名 `.webp`（**尺寸与比例必须和原图一致**，否则坐标换算整体偏移），
  刷新页面；清单没变就不用动 `maps.json`。
- **加一张地图**：见 `public/game/README.md` 三步。要点：`img` 只写文件名、`maxX/maxY` 是走一遍四角
  量出来的真实坐标域、跑 `npm run check`（测试读真实清单，缺图当场失败）。
- **换一批数据表**：改 `data/*.json`（加一个门派就加一个对象，`skills` 仍是七项、`id` 仍是拼音小写）
  → `npx vitest run src/services/game-data.test.ts`（形状、条数、id、重名都在这里盯）→ 刷新即生效。
  数据表异步加载，但异步只留在边界：`main.ts` 里等待 `loadGameData()` 首次尝试结束后 `mount`，
  之后全站同步读缓存。首次失败时由角色页使用 `game-data.ts` 的统一状态与重试入口；
  **不许**在各组件里自行 `fetch` 或维护另一份资源加载态。
- **补一批图标**：① 进游戏打开对应面板，一页一张截图，原分辨率、别经聊天软件压缩；② 把图放进
  `slice.py` 的 `PAGES`（门派放 `slice-school.py` 的 `PANELS`），写清每页应有几项；③ 跑脚本
  （门派先 `--check` 校名字再写文件），数量对不上直接报错退出，图会落进同名子目录；④ 看
  `data/*-icons.json` 里新加的名字对不对（脚本从 `skills.json` / `schools.json` / `character-rules.json` 读
  名字，读不到会报错）；⑤ `npm run check`。
- **加一个全新类目**（如任务类型图）：新建 `icons/task/` + 一条 `slice-*.py` + 一份
  `data/task-icons.json`，再在 `services/game-icons.ts` 加**一条目录常量**和一个取值函数。三处缺一处
  都会表现成「图在但查不到」或「查得到但 404」。
- **游戏大版本更新时**照这张表过一遍：`maps/`（新场景、坐标域）｜`data/`（门派、技能、等级上限）｜
  `icons/`（名字增删，改了要重切，序号会整体错位）｜`DEFAULT_ROI`（用探针截一帧量，别目测）｜
  `ghost-parse.ts` 的句式（尤其「去」「的」「附近」）｜`TITLE_HINTS`｜`CONFUSABLE`。

```bash
grep -rn "game/" src --include="*.ts" --include="*.vue"   # 目录是否被写死在代码里（应只剩 DIR 常量与 4 个测试字面量）
npx vitest run src/services/ghost-maps.test.ts src/services/game-icons.test.ts   # 缺图 / 孤儿图 / 串门 / id 重复
ls public/game/icons                                       # 根下有没有散图
npm run check                                              # 上面两条也在里面
```

第 2 条不是可选检查，是 `npm run check` 的一部分。新增一类游戏资源时照着补一组同样的断言：
**规范里承诺的保障，必须有一条会红的测试撑着，否则它只是愿望**。
