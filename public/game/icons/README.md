# public/game/icons/ —— 游戏内的图标与图片

门派徽记、技能图标、任务类型图、NPC / 怪物头像、道具图标这类**游戏里能看到的小图**。

与 `src/components/icons.ts`（tabler 那套界面图标）不是一回事：那是**界面语言的图标**，
这里是**游戏内的图**，两者不混用、不互相替换。

## 结构：一个类目一个文件夹

```
icons/
├── README.md
├── skill/     skill-01..21.webp           生活技能 21
├── story/     story-01..11.webp           剧情技能 11
├── active/    active-01..69.webp          装备特技 69
├── school/    school-skill-<门派>-<n>.webp 门派技能 147
├── gear/      gear-<部位>-<nn>.webp        装备 83
├── weapon/    weapon-<种类>-<等级>.webp    武器 231
├── item/      item-<id>.png|gif            速记物品 59
├── lingshi/   ling-<部位>-<等级>.webp      灵饰 20
└── yupo/      yupo-<yin|yang>.webp         玉魄 2
```

两条规则，只说两句话：

1. **根目录不许放图**。一个类目一个子目录，将来加召唤兽、宝石、任务图，就新建一个同名目录。
2. **文件名以目录名开头**：`skill/skill-01.webp`、`school/school-skill-datang-1.webp`、
   `gear/gear-toukui-01.webp`。目录名是**一级类目**，文件名 = 一级类目 [+ 二级类目] + 序号。

两条都由 `src/services/game-icons.test.ts` 的「图标目录结构」那组断言盯着：一张图丢在
`icons/` 根下、或一个目录里住了两个类目，`npm run check` 当场红。

**为什么值得为这件事写测试**：这批文件会一直长（2026-11-04 一天从 268 涨到 390），而
「往 `icons/` 里丢一个新 png」是最省事的写法，谁都不会觉得有问题——直到根目录有 800 个
文件，只能靠前缀猜「这张是谁的」。规范没有断言撑着就只是愿望（`docs/GAME-ASSETS.md` §9）。

| 目录       | 内容     | 数量 | 来源                                                                                        |
| ---------- | -------- | ---- | ------------------------------------------------------------------------------------------- |
| `skill/`   | 生活技能 | 21   | 「生活技能」目录两页（第一页 12、第二页 9）                                                 |
| `story/`   | 剧情技能 | 11   | 「剧情技能」目录一页                                                                        |
| `active/`  | 装备特技 | 69   | 「特技特效」面板六页（12×5 + 9）                                                            |
| `school/`  | 门派技能 | 147  | **客户端资源包原生 PNG**，21 家门派 × 7 项，见 `../data/school-icons.json` 的 `source`      |
| `gear/`    | 装备图标 | 83   | **客户端 `item120` 大图**，7 部位 × 60~160，见 `../data/gear-icons.json`                    |
| `weapon/`  | 武器图标 | 231  | **客户端 `item120` 大图**，21 组（双巨斧拆乾/坤，各 11 张），见 `../data/weapon-icons.json` |
| `lingshi/` | 灵饰图标 | 20   | **客户端 `item120` 大图**，4 部位 × 60~140，见 `../data/lingshi-icons.json`                 |
| `item/`    | 速记物品 | 59   | 摆摊掉落物（38 件有牌价 + 21 件随行就市），见 `../data/quick-items.json`                    |
| `yupo/`    | 玉魄图标 | 2    | **客户端 `item120` 大图**，上古玉魄·阴 / ·阳；不分级，无清单，见下文                        |

`item/` 文件名里的数字是 `quick-items.json` 的 **id**（不是序号），因为 id 才是单价表的键；
`gear/` 那批是**序号**，序号本身即等级升序（第 1 个 = 60 级），单件名称在清单的 `name` 里。
`weapon/` 的文件名**直接带等级**（`weapon-jian-060`），因为武器种类多、光靠序号找不着；
90 级起的几款一件覆盖 90-150，同区间多款用 `b`/`c` 后缀（`weapon-jian-090b` 是「倚天」）。
**双巨斧例外**：它在客户端是乾、坤两件，多一段 `-qian` / `-kun`，后缀仍用 `b`/`c`
（`weapon-shuangjufu-qian-090b`）。两组各到 160 结束（`weapon-shuangjufu-qian-160` 是「非天（乾）」）。
`lingshi/` 同样**带等级**（`ling-jiezhi-060`）——一个部位只有 5 件，序号反而更难找。

`yupo/` 只有两件，按「阴 / 阳」命名（`yupo-yin.webp` / `yupo-yang.webp`）。这一族有**三个不同的
名字**，改的时候别照着格子名拼路径：客户端叫「上古玉魄·阴」、装备格的 key 是「玉魄·阴」、
文件名是 `yupo-yin`。两者之间只靠 `character.ts` 的 `GEAR_SLOT_ICON` 那两行对上。
**这两件不写清单**：总共两条固定记录，清单只会变成第二份真源，而它没有第二个消费方。

装备特效（18 项）**没有图标**：游戏那一页只有名字，没有图形，所以 `active/` 里只有特技。

师门法术（面板中间那一列，墨绿，45 个）**不收**：使用方只要门派技能。
面板里那 7 个格子之外的图，在 `../data/schools.json` 里也没有对应字段。

清单与目录一一对应，别混：

- `skill/` `story/` `active/` → `../data/icons.json`（`slice.py` 生成）
- `school/` → `../data/school-icons.json`（名字与顺序是 `slice-school.py` 的产物，**图与 `source` 由 `import-school-icons.py` 覆写**）
- `gear/` → `../data/gear-icons.json`（`import-slot-icons.py` 写图与 `source`，名字表仍是 `slice-gear.py` 的）
- `weapon/` → `../data/weapon-icons.json`（`import-slot-icons.py` 写图与 `source`，名字表仍是 `slice-weapon.py` 的）
- `lingshi/` → `../data/lingshi-icons.json`（`import-client-icons.py` 生成）
- `item/` → `../data/quick-items.json` 的 `file` 字段（旧系统带过来的图，不是切图产出）
- `yupo/` → **没有清单**（两件固定记录，路径直接写在 `GEAR_SLOT_ICON` 里）

清单分开写是因为每个脚本的裁切逻辑完全不同（4×3 卡片网格 / 竖排 7 行面板 / 3×4 方格且
可滚动），写同一份清单时谁后跑谁把对方的分组覆盖掉——那种丢失不会有任何报错。

**`lingshi/` 这批只有 20 件，不是 24**：面板按「种类 → 等级」排，四个部位 × 60/80/100/120/140，
到 140 就结束了（第二张截图最后一行第三格是空的）。官网介绍页另列了 160 级那四件
（太虚渺云 / 焰云霞珠 / 浮雪幻音 / 碧海青天），**这个客户端里没有**，别照着官网表补齐——
补出来的图只能是自己画的。

2026-11-05 起这 20 张**不再来自百科典藏的列表截图**，改成直接导入客户端资源里的 `item120`
（大图，透明底）。截图那条路的问题不在裁得准不准，而在一格只有 94×94 且**自带游戏卡片底**：
放到 40px 就是一块米黄方片，四角还带着卷云暗纹。换来源之后四个灵饰格与其它品类一样是透明图，
底色交给 `IconTile` 的块面。旧脚本 `slice-lingshi.py` 已删，取舍写在 `docs/RECORD.md` 第 116 批。

**`玄龙苍珀`（佩饰 140）是唯一没有大图的一件**：它的 `item120` 资源在本地客户端里缺失
（提取工程的 `missing-images.csv` 记着 21129 个本地找不到的图资源），只能用 `item50`
放大。清单里该条 `source` 写的是 `item50`，其余 19 条是 `item120`——**能不能换掉看有没有新客户端**，
不要拿官网小图凑。

拿到图之后 `views/characters/character.ts` 的 `GEAR_SLOT_ICON` 已从 `ling-01.png` 这类
占位名改成 `lingshi/ling-<部位>-060.webp`（60 级那件当部位示意图），卡上那四格不再是破图。

文件名是**序号**，不是技能名：`skill-01` 就是 `skills.ts` 里 `LIFE_SKILLS[0]`（强身术）。
序号与名字表的对应关系写在清单里，并由 `src/services/game-icons.test.ts` 用断言盯着——
**第 n 个图标的名字必须等于名字表的第 n 项**。

门派那一批的序号是**面板里的上下顺序**，不是 `data/schools.json` 里 `skills` 的顺序
（后者按重要度排，大唐的「十方无敌」在面板第 1 位、在表里第 5 位）。所以查图标**按名字**、
不要按 `schools.json` 的下标推——`school-icons.json` 里每一条都写明了 `name`。

为什么不用拼音做文件名：这些名字是批量产出的（101 个），手写拼音容易拼错，而拼音库在
离线环境装不上；序号 + JSON 映射反而更可靠，且与名字表的数组下标天然对齐。代价是
「看文件名猜不出是什么」——那就在 `icons.json` 里查，或者看开发页。

## 重新生成

游戏改版、或者补了新一页目录，重新跑：

```bash
python tools/game-icons/slice.py             # 生活 / 剧情 / 特技 → skill/ story/ active/ + icons.json
python tools/game-icons/slice-school.py      # 门派技能的名字与顺序 → school-icons.json（图随后被下一条覆写）
python tools/game-icons/slice-gear.py        # 装备（名字与顺序的基准）→ gear-icons.json
python tools/game-icons/slice-weapon.py      # 武器 → weapon/ + weapon-icons.json
python tools/game-icons/import-client-icons.py # 灵饰 + 玉魄（客户端大图）→ lingshi/ yupo/
python tools/game-icons/import-slot-icons.py   # 装备 + 武器（客户端大图）→ gear/ weapon/ + source
python tools/game-icons/import-school-icons.py # 门派技能（客户端原图）→ school/ + source
```

`skill/` `story/` `active/` 三批从截图切，其余**都不从截图来**。

**门派技能要连着跑两条**（`slice-school.py` → `import-school-icons.py`）：前者会整份重写清单、
把图和 `source` 一起打回截图那版，所以它只负责名字与顺序，图由后者覆写。这与装备 / 武器
「先 `slice-gear`/`slice-weapon` 再 `import-slot-icons`」是同一条约定。

`import-client-icons.py` 读提取工程的 `output/names.csv`，按物品名取 `item120`（大图）那一档
的 PNG；`--src` 换提取目录，`--only yupo` 只跑玉魄，`--check` 只报告不写盘（会告诉你哪几件
缺大图、退到了 `item50`）。

`import-slot-icons.py` 处理**装备 83 件 + 武器 231 件**，它**不按名字取图**——同名物品在客户端
里不止一个（`如意` 同时是环圈、法宝、道具），按名字会静默抓到别的道具。改为按**物品编号段**
定位：武器每组用「候选 id − 偏移」投票求起始编号（票数不过半直接退出），装备限定在
`2000–2999` 段内再用相邻锚点收敛；最后还有一道「解析出的编号必须沿清单递增」的断言。
它只覆写图片与清单里的 `source`，**不改 id / 名称 / 等级 / 顺序**——那些是 `slice-gear.py`
与 `slice-weapon.py` 的产物。`--only gear|weapon` 分组跑，`--check` 只报覆盖率。

**顺序是先 `slice-*` 再 `import-slot-icons`**：`slice-gear.py` 会整份重写清单（删掉 `source`、
把 `generated-by` 改回自己），单独跑它等于把图和清单一起打回截图那版。

`slice.py` 一次写三个目录（`skill/` `story/` `active/`），因为那三批来自同一个 4×3 卡片
面板、共用一份清单；它收的参数是**图标的根**（`public/game/icons`），不是某一类的目录。

`slice.py` 从截图里按 4 列 × 3 行的网格切出图标，统一成 96×96、**图标本体铺满画布、不垫
任何背景**，并重写自己的清单。截图路径与每页的期望数量写在脚本顶部的 `PAGES` 里——**数量
对不上会直接报错退出**，不会切一半就写完。

`slice-school.py` 的裁切逻辑现在**只服务名字与顺序**：它切出来的图会被
`import-school-icons.py` 整批覆写（2026-11-07，第 139 批），所以 `PANELS` 与 `body_bottom()`
那套仍然要能跑通，但画面质量不再由它决定。

`slice-school.py` 还有两道校验，都在写盘之前：

- **名字**：脚本里抄的名字与 `../data/schools.json` 的那一家做**集合**比对（按集合不按顺序，
  两份顺序本来不同），抄错一个字会当场列出来；加 `--check` 可以做干跑。
- **底边**：`body_bottom()` 逐格量。同一批 21 张截图里，最后六张（女魃墓、天机城、花果山、
  东海渊、九黎城、弥勒山）的图标列比前十五张高 1px，它们最底下一行是「描边 + 米黄底」混出来的
  **半透明行**，留在图里就是一道黄边。判据是"跳变行比上一行亮就丢掉"：前十五家那一行是深色
  描边（比上一行暗 10~23 级），这六家是混合行（亮 7~50 级），两类差 17 级，不会误判。
  结果各家 7 格高度一致（15 家 59 行、6 家 57 行）。

**别想靠补整数像素解决底边**：先试过 `dy: -1` 手工补偿，没用——半透明行换成哪个整数位置都在。
加 `--report` 可以只打印每家的本体高度、不写文件，换新截图时先跑它看一眼。

### 门派技能为什么改从客户端导入（2026-11-07，第 139 批）

上面那套裁切与底边判据全部是**截图那条路的补丁**，而截图这条路本身就拿不到清晰度：面板里
一格图标本体只有 **60×59**，缩到 96 是**上采样**；那 60×59 又是游戏把 40×40 的源放大渲染进格子
的结果，中间已经插值过一次；最后再过 webp q92 有损。三层叠起来就是「像素 96、信息 40×40」，
在卡上与 `gear/` `weapon/`（客户端 120 大图）并排时明显软一档。

现在直接取客户端资源包里的原生 PNG（40×40，8 张 30×30），LANCZOS 归一到 96×96。
147 对按 48px 真实显示管线实测：

| 指标                          | 截图切（旧） | 客户端原图（新） |
| ----------------------------- | ------------ | ---------------- |
| 48px 显示下的拉普拉斯方差中位 | 2416         | **4123（+71%）** |
| 新图更锐的项数                | —            | **146 / 147**    |

唯一变差的是「弥勒山 / 慈悲为怀」（源 30×30，48px 下 1282 → 1204，降 6%）。那 8 张 30×30 是提取侧刻意选的
SP 版（十方无敌 + 弥勒山七项），理由是图案与面板更一致——代价就是像素基数小一档，清单里
`source` 记成 `client30`，将来客户端若有 40 版就能一眼找回来。

**底色问题反过来了**：这批图标自带红棕卡片底（游戏里就长这样），新旧都带，换来源不影响；
而 `body_bottom()` 当年除掉的「末行黄边」在新图里不存在——源是 40×40 整图，没有半行可带。

## 命名（新增图标时）

```
<目录>/<类目>-<id>.webp
<目录>/<类目>-<子类>-<id>-<序号>.webp    # 一个实体有多个图标时
```

- **目录 = 一级类目**：`skill` / `story` / `active` / `school` / `gear` / `weapon` / `item` /
  `lingshi`。以后的任务图、NPC、怪物各开一个同名目录（`task/`、`npc/`、`monster/`）
- **文件名必须以目录名开头**：`school/` 里放 `school-skill-…`，`gear/` 里放 `gear-…`。
  测试会拒绝「一个目录里住两个类目」
- id：与 `data/` 里对应记录的 `id` 一致，小写拼音或英文短词（`school-datang.webp`）
- 中间用**半角连字符**，不用空格、不用中文——文件名要进 URL
- 门派技能必须带子类：`school-skill-datang-1.webp`，**不要写成 `school-datang-1`**——
  那样与「门派徽记 `school-datang.webp`」挤在同一族里，看文件名分不清是徽记还是第 n 项技能

## 尺寸与格式

- `.webp`，有损 `quality=92`（101 个图标合计 406KB；无损要 957KB，而图标最大只按
  48px 显示，肉眼无差。门派技能那 147 个纹样更密、且换成客户端原图后细节更多，合计 474KB）
- 边长 **96**：界面按 48px 显示也够 2 倍屏，再大只是浪费体积
- **`gear/` `weapon/` `lingshi/` `yupo/` 是 120×120 的例外**（`gear/` 第 120 批、`weapon/` 第 121 批）：这四批是
  客户端大图的原尺寸归一到 120（最长边 108、居中），缩到 96 等于把大图又丢一档，而 40px 的
  槽位在 2 倍屏要 80px，120 留了一次放大余量；装备 83 张合计约 538KB、灵饰 20 张约 176KB，
  不值得为省几十 KB 再缩。**同一类目内部仍然同尺寸**，这条例没破
- **图标本体铺满画布，不垫背景色**：早先垫了一圈游戏卡片底的米黄（`(230,196,155)`），
  看着像「画在游戏卡片上」，实际用起来就是图标外面套了一圈黄边——底色该由用它的地方决定
- **也不要「补成正方形」**：门派技能本体是 60×59，补那 1px 若填黑，就成了上下各一条黑边，
  看着正好像图标被截断。直接用 96×96 缩放，1.7% 的各向异性看不出来
  （`lingshi/` 例外：那批是**透明**画布上居中，补出来的边是透明的，不会读成截断）
- **同一类目的图标必须同尺寸**：一排图标里混着 88 和 96，基线就对不齐

## 为什么不在截图上抠底

`weapon/` 一度是唯一还带卡片底的一批（每张一块米黄小方片）。2026-11-05 第 121 批也换完了：
231 张全是客户端 `item120` 大图、120×120 透明底，`source` 一律 `item120`——
**装备 / 武器 / 灵饰 / 玉魄 这四批现在都不带底。**

**但「`icons/` 下一张带底的都没有」是句错话**（这句以前写在这里，2026-11-07 更正）：
`school/` 那 147 张**一直带着红棕卡片底**，因为它是从师门面板截图切的，格子自带底。
第 139 批换成客户端原图之后**照旧带底**——客户端里这枚图标本来就画在底板上，那是图案的一部分，
不是可以剥掉的背景。所以准确的写法是：**透明底的是那四批 120×120 的装备族；`school/` 带底，且是刻意的。**

当初为什么不抠：装备/武器图标本来就画在游戏卡片上，图形与卡片底**同色系**。
实测白衣 `(240,240,235)` 与卡片底 `(243,222,192)` 的曼哈顿色差只有 64，
而卡片底自身在格子里的渐变跨度就有 44——两者分不开。试过 flood fill（从四边连通填充）
加腐蚀去堵轮廓缺口，结果是女衣、项链那几页必定出现米色大洞（白色装备被当成背景挖掉），
比带底更难看。

所以截图那几批**只做裁切、不抠底**（格子边内缩 2px → 裁 90×90 → 缩到 96×96），
留白多少由游戏原图决定，不替它决定。

三次换来源都不是「抠图抠成功了」，而是换了一个本来就没有卡片底的来源：`lingshi/` 第 116 批、
`gear/` 第 120 批、`weapon/` 第 121 批。**以后再遇到带底的图，同样换来源，不要在截图上抠。**

第四次（`school/`，第 139 批）换的理由不一样：客户端原图**也带底**，换它是为了拿到**原生像素**
而不是截图的二次放大。但两次的结论是同一条——**图不对就换来源，不要在图上修**。现在真正还
从截图切的只剩 `skill/` `story/` `active/` 三批（21 + 11 + 69 = 101 张），它们与卡片底同色系，换不动。

### 裁得对不对，看四个格子的交汇处

卡片四角各有一朵**卷云暗纹**，四个相邻格子的四分之一拼起来，正好是一个完整对称的四瓣花。
这是验收标准：把图无缝拼成棋盘，四瓣齐全就是裁对了，缺一瓣就说明那一张的取景偏了。

据此定下两条硬规矩：

1. **内缩不能超过 2px**。内缩 4 会把云纹的角切掉，拼图时四瓣缺一角（2026-11-05 返工时踩到）。
2. **底边不能兜到面板边界**。列表最底那一行被面板下边缘切掉，裁出来的图底部会带一条
   格子间隙，拼图时就是一道横贯的亮带。`has_band()` 会拒收这种格子，让合并流程去别的页
   取同一行完整的那份；实在只有这一份可用的（`weapon-mobang-160`），整体上移 2~8px 重取。

**`weapon/` 不要改成「取内容包围盒再等比放大」**（踩过，2026-11-05 返工）：
那个写法看着更"整齐"，两个后遗症都很显眼——图标被拉满到贴边，像是被裁掉了；
贴顶的图标会把取景框顶到格子外面，带进来一条更亮的格子间隙。当时还有第二层错：
行定位用的是「内容投影 - 2px」，而图标贴不贴格子顶因图而异，于是每页各偏 2~8px，
表现就是「有的上面多一条边、有的少一截」。现在行定位改成**用格子间隙求相位**
（间隙位置与图标无关），取景改成固定内缩，两处都不再依赖图标长什么样。

要透明版就**换素材来源**（游戏资源包里的图标原图），不要在这批截图上继续抠——`lingshi/`
与 `gear/` 都已经这么换过两回了，只剩 `weapon/` 停在截图上，等客户端补完那 30 张。

`gear-icons.json` 目前**没有任何测试盯着**（另两份清单有 `game-icons.test.ts` 比对名字）。
数量与顺序的保障眼下靠脚本自己：`slice-gear.py` 里 `NAMES` 与裁出的张数不一致会直接报错退出。
等装备页落地、`data/gear.json` 补上属性字段，再照 `game-icons.test.ts` 补一组同样的断言。

## 引用方式

和地图一样走运行时路径，不 `import`：

```ts
const url = `${import.meta.env.BASE_URL}game/icons/skill/skill-01.webp`;
```

**目录在代码里只写一次**：`src/services/game-icons.ts` 顶部每个类目一条常量
（`SKILL_DIR` / `STORY_DIR` / `SCHOOL_DIR` / `ITEM_DIR`），`gearSlotIcon` 那族由调用方
自带子目录（`gear/…`、`lingshi/…`）。组件里不许拼路径——那样换一次目录要改十几处，
而漏掉的那一处只在运行到那张图时才 404，页面上什么都不报。

图标与数据表一一对应时，把文件名写进对应的 `data/*.json`（只写文件名），目录由上面那些
常量拼。
